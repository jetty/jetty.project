= JASPI

Enabling this module allows Jetty to utilize authentication modules that implement the Jakarta Authentication (JASPI) specification.
JASPI provides an SPI (Service Provider Interface) for pluggable, portable, and standardized authentication modules.
Compatible modules are portable between servers that support the JASPI specification.
This module provides a bridge from Jakarta Authentication to the Jetty Security framework.

Only modules conforming to the "Servlet Container Profile" with the ServerAuthModule interface within the https://jakarta.ee/specifications/authentication/3.1/jakarta-authentication-spec-3.1.pdf[Jakarta Authentication] specification are supported.
Each environment implements the version its EE platform defines: EE8 is JASPIC 1.1, EE9 is Jakarta Authentication 2.0, EE10 is 3.0 and EE11 is 3.1.
The EE8 types are in the `javax.security.auth.message` namespace, so its factory is `javax.security.auth.message.config.AuthConfigFactory` and Jetty's classes for it are in `org.eclipse.jetty.ee8.security.jaspi`.

In every environment a module can be configured before start-up, or registered and de-registered at runtime on the `AuthConfigFactory` obtained with `AuthConfigFactory.getFactory()`.
A module is registered by passing an `AuthConfigProvider` to `registerConfigProvider`, either your own or Jetty's `JaspiAuthConfigProvider`, which wraps a `ServerAuthModule`.
The application context to register it for is the name of the logical host, a space, and `ServletContext.getContextPath()`.
The name is `ServletContext.getVirtualServerName()`, which is null for a context with no virtual host, and Jetty substitutes `server` for it,
so a context at `/test` with no virtual host is registered as `server /test`.
A provider registered after the context has started is used from the next request, but `registerConfigProvider` does not remove it when the context stops,
so a `ServletContextListener` that registers one should call `removeRegistration` from `contextDestroyed`.

In EE10 and later a web application can instead register its own `ServerAuthModule` from a `ServletContextListener` or a `ServletContainerInitializer` by calling `registerServerAuthModule(ServerAuthModule, ServletContext)`,
and remove it again with `removeServerAuthModule(ServletContext)`; these methods were added in Jakarta Authentication 3.0.
A module registered that way is removed when its context stops, so it needs no `removeRegistration`.

[CAUTION]
====
Enabling a `jaspi` module exposes the Jakarta Authentication API to the web applications in that environment,
and the `AuthConfigFactory` they reach is process wide.
A web application can register a provider for an application context it does not own,
either as the fallback for the contexts that have no provider of their own,
or under another context's identifier, replacing what that context registered,
and so choose the caller principal and the roles that context sees.
`setFactory` and `removeRegistration` reach as far, and `getRegistrationIDs(null)` lists every registration in the process, so the identifiers need not be guessed.
Do not enable a `jaspi` module on a server hosting web applications that do not trust each other.

=== Configure JASPI

Activate the `{ee-all}-jaspi` module, whichever matches your EE platform version.

[source,subs=attributes+]
----
$ java -jar $JETTY_HOME/start.jar --add-modules={ee-current}-jaspi
----

You can then register a `AuthConfigProvider` onto the static `AuthConfigFactory` obtained with `AuthConfigFactory.getFactory()`.
This registration can be done in the XML configuration file which will be copied to `$JETTY_BASE/etc/jaspi/jetty-{ee-current}-jaspi-authmoduleconfig.xml` when the module is enabled.

=== Integration with Jetty Authentication Mechanisms

To integrate with Jetty authentication mechanisms you must add a `LoginService` to your context.
The `LoginService` provides a way for you to obtain a `UserIdentity` from a username and credentials.
JASPI can interact with this Jetty `LoginService` by using the `PasswordValidationCallback`.

The `CallerPrincipalCallback` and `GroupPrincipalCallback` do not require use of a Jetty `LoginService`.
The caller principal and the groups they establish become the `UserIdentity` of the request directly, with the groups as its roles.

=== Replacing the Jetty DefaultAuthConfigFactory

Jetty provides an implementation of the `AuthConfigFactory` interface which is used to register `AuthConfigProviders`.
This can be replaced by a custom implementation by adding a custom module which provides `{ee-all}-auth-config-factory`.
This custom module must reference an XML file which sets a new instance of the `AuthConfigFactory` with the static method `AuthConfigFactory.setFactory()`.
For an example of this see the `{ee-current}-jaspi-default-auth-config-factory` module, which provides the default implementation used by Jetty.

----
